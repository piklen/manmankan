## 1. 触发原因

v0.0.2 发版后 `kan/cli.py` 行数 = **1512 行**。
单文件超过 1000 行是常规可读性 / SRP 红线。

具体职责混杂：
- 12 个 typer 命令（add / remove / list / import / clear / scan / low / high / trend / info / fetch / update / uninstall / completion）
- 6 类 helper（错误脱敏 / 网络异常友好化 / 进度条 / 安装方式检测 / shell 检测 / argv normalize）
- 2 个 atexit hook（completion 自动安装 / update 自动检查）
- 1 个 entry（cli_main）

合并到一个文件让任何一类改动都要重新滚屏定位 · 多人协作冲突概率高。

---

## 2. 拆分目标

- **每个文件 < 350 行**
- **单一职责**：一个文件只承担一类工作
- **测试隔离**：改一个命令组不影响其他文件
- **保持现有性能**：lazy import 模式延续 · 不破坏 v0.0.2 冷启动优化
- **零行为变更**：用户视角无任何感知差异

---

## 3. 拆分方案（选项 D · 7 文件）

```
kan/
├── app.py                # NEW · typer.Typer 单例隔离
├── cli.py                # 极薄 entry · ~80 行
├── cli_helpers.py        # 共享 helper · ~150 行
├── cli_watchlist_cmds.py # add/remove/list/import/clear/help · ~280 行
├── cli_scan_cmds.py      # scan/low/high/info/fetch + auto_fetch_stale · ~340 行
├── cli_trend_cmds.py     # trend · ~150 行
├── cli_meta_cmds.py      # update/uninstall/completion · ~280 行
└── cli_atexit.py         # _auto_install_completion + _check_updates_atexit · ~280 行
```

**为什么单独抽 `app.py`**：避免循环 import。
- 子模块需要 `@app.command()` 装饰器引用 `app`
- 如果 `app` 在 cli.py，子模块要 `from kan.cli import app` → cli.py 又要 import 子模块触发命令注册 → 循环
- `app.py` 单独存放 `app = typer.Typer(...)` 单例，cli.py 和所有子模块都从这里 import，无循环

---

## 4. 设计模式应用

| 模式 | 应用位置 | 收益 |
|---|---|---|
| **Singleton** | `kan/app.py::app = typer.Typer(...)` | 全局唯一注册中心 · 子模块共享 · 避免循环 import |
| **Command pattern**（隐式） | `@app.command()` 装饰器 | typer 已实现 · 每个命令是独立 callable |
| **Module-as-namespace** | `cli_*_cmds.py` 按命令组划分 | SRP · 每个文件只关心一组命令 |
| **Strategy pattern** | `kan/updater.py::detect_install_method()` | 不同安装方式（uv tool/pipx/pip）不同 upgrade strategy |
| **Lazy import** | 子模块**顶层**不 import rich/重模块 · 函数体内 lazy | 延续 v0.0.2 冷启动优化 |

**反过度抽象的边界**：
- ❌ 不引入 `commands/` 子目录（增加路径深度但不产生显著好处）
- ❌ 不创建 `BaseCommand` 抽象基类（typer 已经把命令变成 function · 加 class 反而冗余）
- ❌ 不引入 dependency injection 框架（小工具不需要）

## 5. Trade-off 分析（架构师必须做的事）

### 5.1 采用拆分

**优点**：
- 单文件 < 350 行 · grep / 阅读 / 定位快
- 命令独立测试 · 改一处不影响其他文件
- 新增命令只需加一个文件 + 注册 · 不动主入口
- 多人协作 git conflict 概率低（不同人改不同文件）
- 符合单一职责原则（SRP）

**缺点**：
- 文件数量从 1 → 8 · 项目层次更深
- import 链变长（虽然 lazy import 已 mitigate）
- 现有 grep `kan.cli` 的 documentation / 测试需要更新
- 跟现有 `kan/scanner.py` / `kan/watchlist.py` 等单文件大模块风格不一致（manmankan 整体风格偏单文件）
- **过度抽象风险**：v0.0.1 review §4.7 LOCKED「不要过度抽象」准则可能反向

### 5.2 不拆分（保持单文件）

**优点**：
- 所有命令一处可见 · grep 找定义快
- import 链浅 · 启动稍快（虽然 lazy import 已让差异 < 1ms）
- 改动小 · 风险低
- 文件数量不膨胀
- 符合 v0.0.1 review §4.7「不要过度抽象」准则

**缺点**：
- 单文件 1512 行 · 阅读 / 定位 / 多人协作低效
- SRP 违反明显
- 测试隔离差（改 add 命令也需要 reload 整个 cli.py）

### 5.3 判尺（什么时候该拆 / 什么时候不拆）

| 应该拆 | 不应该拆 |
|---|---|
| 单文件 > 1000 行 | 单文件 < 500 行 |
| 不同命令组之间没有强耦合 | 命令间共享大量内部 helper |
| 已有 lazy import 模式 | import 成本敏感 / 没有 lazy 模式 |
| 测试覆盖足够（重构有保护网） | 测试覆盖不足 |
| 有明确的功能分组（如自选股 / 扫描 / 元命令） | 强耦合无明显边界 |

**manmankan 当前**：1512 行 + 命令组耦合度低 + lazy import 已就位 + 207 测试覆盖 → **5 个判尺全部满足 · 拆分合理**。

### 5.4 最终决策

**采用选项 D 拆分**。在 v0.0.3 单独 PR 实施。

## 7. 风险

1. **typer sub-app 注册时机**：必须确保 cli.py 顶层 import 子模块触发 `@app.command()` 装饰器执行。子模块 import 顺序错误可能导致部分命令未注册。
   - 缓解：`kan/cli.py` 文件末尾显式 `from kan import cli_watchlist_cmds, cli_scan_cmds, ...`（用 `# noqa: F401` 标注 unused）
2. **测试 fixture 涉及 cli 内部函数**：`test_*_cli.py` 可能直接 import `kan.cli._safe_error_msg` 等 private helper · 拆分后路径变化。
   - 缓解：拆分前 grep `from kan.cli import` 列出所有引用 · 同步更新
3. **Lazy import 边界不清**：抽出的子模块容易在顶层 `import rich` / `import xxx` 破坏 v0.0.2 优化。
   - 缓解：CR 时 grep 子模块顶层 import 行 · 严格只允许标准库 + typer + 自身项目模块
