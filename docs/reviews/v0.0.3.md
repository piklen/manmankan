# v0.0.3 · CLI 启动 silent 期审计

> 时间：2026-05-12
> 版本：v0.0.3（CLI 拆分后回归审计）

---

## 1. 现状审计

v0.0.3 已完成 `kan/cli.py` 拆分，但数据命令仍存在启动可见反馈不足的问题。
本地 PTY 真终端测量结果：

| 命令 | TTFB | spinner 第一帧 | 结论 |
|---|---:|---:|---|
| `kan --help` | 58ms | N/A | 达标 |
| `kan add 002792` | 49ms | 133ms | 达标 |
| `kan scan` | 494ms | 495ms | 未达 200ms SLO |

源码环境补充测量显示，`scan` 在一只自选且无 K 线缓存时，spinner 第一帧约
699ms；`fetch 600519 --force` 无 spinner，首个输出约 1.16s 后才出现。

## 2. 根因

`kan/fetcher.py` 顶层仍有：

```python
import akshare as ak
import pandas as pd
```

`kan/scanner.py` 顶层仍有 `import pandas as pd`。`scan` / `low` / `high` /
`trend` / `info` 入口在函数体开头直接 import `kan.fetcher`、`kan.scanner`、
`kan.render`，导致 `rich.Progress` 或后续输出出现前，先付了 pandas / akshare /
numpy 等重依赖加载成本。

## 3. v0.0.4 修复期望

SLO：

| 命令 | 目标 |
|---|---:|
| `kan scan` | spinner 第一帧 ≤ 200ms（aspirational；真实 wrapper 受 Python startup 约束，回归阈值按 400ms） |
| `kan fetch` / `low` / `high` / `info` / `trend` | spinner 第一帧 ≤ 200ms（aspirational；真实 wrapper 回归阈值按 400ms） |
| `kan add` | 不回归，spinner 第一帧 ≤ 200ms（真实 wrapper 回归阈值按 400ms） |
| `kan --help` | TTFB ≤ 100ms |

范围：

- `fetcher.py` 顶层移除 `akshare` / `pandas`，按使用点 lazy import。
- 数据命令入口用 stderr `console.status(..., spinner="dots")` 包住重模块 import。
- `scanner.py` 可保留顶层 pandas，由入口 spinner 覆盖，不为追求纯 lazy 破坏可读性。
- 新增 PTY 真终端测试，避免 pipe 模式误判 rich spinner。

## 4. 漏修原因复盘

v0.0.2 的修复聚焦 `kan add`：A 股代码表加载路径通过 `paths.py` 做轻量 fresh
检查，并把 spinner 提前到 `watchlist` 重模块 import 之前。这个模式是对的，但当时
只覆盖 watchlist 路径，没有把同样的审计扩展到 K 线数据路径。

v0.0.3 拆分 CLI 时主要目标是结构重构和命令注册稳定性，验证集中在行为不变和测试
全绿，没有补 PTY 首帧 SLO 测试。因此 `fetcher/scanner/render` import 链的冷启动
成本被保留下来。
