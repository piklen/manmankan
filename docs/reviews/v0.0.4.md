## 2. 真实 wrapper SLO 实测

测量方式：`uv tool install --reinstall .` 后，通过 `pty.fork` + `os.execvpe("kan", ...)`
调用真实用户路径。每条命令跑 3 次，取最快值。

```text
cmd                      TTFB(min/3)  spinner(min/3)
kan --help                      42ms            None
kan add 600519                  42ms           134ms
kan scan                        43ms           223ms
kan low 60                      45ms           211ms
kan high 30                     45ms           325ms
kan info 600519                 48ms           305ms
kan trend                       47ms           231ms
```

对照：

| 命令 | 修前 spinner 第一帧 | 修后真实 wrapper 第一帧 | 改善 |
|---|---:|---:|---|
| `kan add 600519` | 约 133ms（v0.0.2 已修） | 134ms | 不回归 |
| `kan scan` | 约 660ms，且部分路径无 spinner | 223ms | -437ms，spinner 可见 |
| `kan low 60` | 约 360ms | 211ms | -149ms |
| `kan high 30` | 约 360ms | 325ms | -35ms |
| `kan info 600519` | 无 spinner，约 1s 后进入拉取输出 | 305ms | 出现 spinner |
| `kan trend` | 约 360ms | 231ms | -129ms |

结论：v0.0.4 的应用层修复有效，但上一版 review 使用 `python -c` bootstrap
测量，跳过了真实 wrapper 和 entry point 成本，报告的 125-135ms 数据偏低。
当前真实 wrapper 回归阈值采用 ≤ 400ms。

## 3. 测试方法修正

`tests/test_cli_silent_period.py` 现在直接执行：

```python
os.execvpe("kan", ["kan", *args], env)
```

如果 `kan` 不在 PATH，测试会 `pytest.skip` 并提示先运行：

```bash
uv tool install --reinstall .
```

上一版的测试方式是：

```python
python -c "from kan.cli import cli_main; cli_main()"
```

这个方式适合源码内函数调试，但不是真实用户路径。它绕过了 `uv tool` 安装后的
console script wrapper、Python 解释器启动和 entry point 解析成本，因此不能用来
报告终端首帧 SLO。

## 4. 取舍与限制

200ms 仍可作为理想目标，但在当前打包方案下不能作为硬性回归阈值。真实用户路径是：

```text
~/.local/bin/kan wrapper
  -> uv tool venv Python
  -> import kan.cli
  -> Typer 注册命令并路由
  -> 命令入口 spinner
```

其中 Python startup、console script wrapper、`kan.cli` 顶层命令注册都有固定成本。
在不更换打包方案的前提下，350-400ms 是更合理的真实 wrapper 回归窗口。

`kan/scanner.py` 仍保留顶层 pandas。原因是 scanner 内部大量 `pd.DataFrame` 和
`pd.Timestamp` 调用，强行 lazy 化会让核心算法可读性下降；入口 spinner 已覆盖
scanner import 成本。

## 5. 后续建议

本次只修启动可见反馈，不优化网络物理耗时。后续可考虑：

- `kan doctor`：诊断数据源、系统代理和缓存状态。
- 持久化熔断器：避免每次启动重复访问短期不可用源。
- 如必须追求 <200ms 首帧，评估 PyOxidizer / Nuitka / Rust shim 等打包或原生入口方案。

## 6. 真冲 SLO 探索记录

### 6.1 方向 1：早期 stderr 文本反馈

做法：在 `kan/cli.py` 顶部、`from kan.app import app` 之前，如果 stderr 是 TTY 且命令
属于 `add/scan/fetch/low/high/info/trend`，先输出：

```text
⏳ 启动中...\r
```

随后 Typer/Rich 正常接管并覆盖同一行。可通过 `KAN_NO_BOOT_BANNER=1` 关闭。

实测：

```text
cmd                      TTFB(min/3)   boot(min/3)  spinner(min/3)
kan --help                      40ms          None            None
kan add 600519                  10ms          10ms           127ms
kan scan                        10ms          10ms           128ms
kan low 60                      10ms          10ms           127ms
kan high 30                     10ms          10ms           126ms
kan info 600519                 11ms          11ms           134ms
kan trend                       10ms          10ms           129ms
```

结论：早期文本反馈成功。它不能减少 Python startup 成本，但能把“按回车后首个可见
反馈”压到约 10-20ms，解决用户看到空屏的心理问题。Rich spinner 首帧在多次测量中
仍有 100-500ms 抖动，因此不能把“spinner 必定 ≤200ms”写成硬承诺。

### 6.2 方向 2：清点 `kan.cli` import 链

`python -X importtime -c "from kan.cli import cli_main"` 显示：

```text
typer        ~15-18ms
kan.app      ~19-27ms cumulative
kan.cli      ~20-29ms cumulative
```

应用层命令模块顶层 import 已经很轻；主要固定成本来自 Typer/Click 注册和 Python
console script 路径。继续把 `cli_scan_cmds` 等命令模块改得更 lazy，收益预计只有个位
毫秒，并且会破坏 Typer 命令注册结构。

### 6.3 结论

在当前 Python entry point 架构下，真正值得落地的是“早期 stderr 文本反馈”，而不是
继续追求每次 Rich spinner 都稳定 ≤200ms。后者需要改变打包/入口形态，建议放到
v0.1 或更大版本评估。
