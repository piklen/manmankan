# v0.0.2 · 冷启动延迟修复

> 时间：2026-05-11
> 版本：v0.0.2（patch 累加 · 性能 hot-fix）
> 维护者：piklen

---

## 1. 本批解决的问题

v0.0.1 用户视角痛点：执行 `kan add 600519 000858 ...` 后，按回车 → 终端 silent
约 10 秒 → 才出现 `⏳ 正在加载 A 股代码表...` 提示 → 再过 5-7 秒结束。
用户合理怀疑「程序卡死了」，第一观感不佳。

---

## 2. 根因分析

v0.0.1 `kan/watchlist.py:14` 顶层有 `import akshare as ak`。akshare 把
pandas / numpy / bs4 / requests 整窝作为间接依赖拖入启动路径。

实测（uv tool 安装的 manmankan venv · 热启动场景）：

| 模块 | cumulative μs | 占比 |
|---|---|---|
| `kan.cli` (不含 watchlist) | 26,735 | floor |
| `kan.watchlist` 总成本 | **268,869** | — |
| └─ akshare | **229,501** | **85.4%** |
| └─── pandas | 136,558 | 50.8% |
| └─── bs4 | 27,308 | 10.2% |
| └─── requests | 24,248 | 9.0% |
| └─ kan.models (pydantic) | 19,872 | 7.4% |

冷启动首次磁盘读 + `.pyc` 编译 + numpy / pandas C 扩展加载，按经验放大
热启动的 3-30 倍——这就是「silent 10 秒」的来源。

akshare 实际上只在 `_fetch_names_akshare()` fallback 路径被调用一次
（baostock 主路径成功时根本用不到），却让所有 add 命令都付了完整 import 成本。

---

## 3. 修复方案（最小侵入 + 极致下限）

### 3.1 akshare 改 lazy import

`kan/watchlist.py` 顶层不再 `import akshare as ak`，改在 `_fetch_names_akshare()`
函数体内 lazy import。baostock 主路径完全不碰 akshare，
从启动路径上消失 85% 成本。

### 3.2 fresh 检查搬到极轻的 paths.py

把 `is_stock_names_cache_fresh()` 和 `NAMES_CACHE_MAX_AGE_DAYS` 从 watchlist.py
搬到 paths.py（paths.py 仅依赖标准库 os / shutil / pathlib · import 成本 ~370μs）。
这让 CLI 可以在 import 重模块（akshare lazy 后仍有 baostock + typer + rich
~1-2s 冷启动）之前先决策。

### 3.3 spinner 提前到重模块 import 之前

`kan/cli.py` 抽 `_load_names_with_optional_spinner` helper：
- 极轻 import `kan.paths.is_stock_names_cache_fresh` 决策 cache 是否新鲜
- cache 过期：`console.status(...)` spinner **包住** `from kan.watchlist import preload_stock_names`
  + 调用 `preload_stock_names()`
- cache 新鲜：spinner 不显示，直接 import + 读 JSON

用户视角：按回车 → 立即看到 `⏳ 正在加载 A 股代码表...` →
5-7 秒后看到 `✅ 加载完成 · 用时 X.Xs` → 进入主循环。**零 silent 期**。

## 4. 测试守护

### 4.1 单元测试 `tests/test_paths.py`

4 个 case 守护 `is_stock_names_cache_fresh()`：
- 缓存文件不存在 → False
- 刚写入（mtime ≈ now）→ True
- mtime ≥ MAX_AGE_DAYS → False
- mtime = MAX_AGE_DAYS - 1（边界）→ True

### 4.2 invariant 测试 `tests/test_watchlist.py::TestColdStartInvariants`

**`test_watchlist_top_level_does_not_load_akshare`**：用 subprocess 子进程
隔离运行 `import kan.watchlist` 然后断言 `'akshare' not in sys.modules`。
sys.modules 是 process-global · 单进程 pytest 内无法可靠检查（其他测试
可能已经把 akshare 拖入），subprocess 是唯一可靠的检查方式。回归保护核心。

**`test_baostock_success_does_not_call_akshare_fallback`**：用 monkeypatch
替换 `_fetch_names_baostock` 返回成功结果 + 替换 `_fetch_names_akshare` 为
sentinel（被调用就抛 AssertionError），断言 baostock 主路径成功时
akshare fallback 不应被触发。

## 6. 这一版的不足（坦诚的）

1. **首次冷启动仍有 ~1-2s import 成本**。akshare 拿掉了，但 baostock +
   typer + rich + pydantic 仍是 floor。spinner 包住了这段，体感无 silent 期，
   但客观 delay 仍存在。继续优化需要换轻量级 CLI 框架（如直接 argparse），
   ROI 不对等。

2. **akshare fallback 路径首次触发仍慢**。baostock 失败时才 lazy import
   akshare，届时 spinner 会多转一圈。这是合理 trade-off：95%+ 用户走主路径
   不受影响，少数 fallback 触发场景额外多等几秒可接受。

3. **没有进程间 import cache**。每次 `kan add` / `kan scan` / `kan info` 都
   各自付 typer + rich 启动成本。长期可考虑 daemon 模式，但单机工具 ROI 极低。

4. **TTY 测试仍是手测**。subprocess invariant 测试覆盖了「akshare 不被
   import」，但 spinner 视觉效果（立即可见 / 动画流畅）依然只能靠
   `script(1)` 手测。pty 自动化测试是技术债。

## 7. 设计原则补充（v0.0.1 review §4 延续）

### 4.8 第三方包默认 lazy import

**触发**：v0.0.1 顶层 `import akshare` 教训。

**原则**：第三方包（特别是 pandas / numpy / scipy / matplotlib / akshare 等
"巨型" 包）默认放在使用它的函数体内 lazy import，不在模块顶层 import。
顶层 import 只允许：
- 标准库
- typer / rich（CLI 主框架，绕不过）
- pydantic（数据 model · import 一次成本可控）
- 自身项目模块

**判断尺子**：单个 import 在 cold start 下成本 > 50ms 即应 lazy 化。

### 4.9 用户视角的"装完即用" = 0 silent 期

**触发**：v0.0.1 「按回车 → silent 10s」用户实感。

**原则**：用户主动操作（按回车 / 点击 / 输入）后，**1 秒内必须有视觉反馈**
（spinner / 进度条 / 文本提示 / 错误信息）。如果操作内部包含重 import，
必须把 spinner 提前到 import 之前显示，让 import 在 spinner 显示后执行。

**工程实现**：把"轻量级决策"（如 fresh 检查）单独搬到极轻模块，让重模块
import 不挡在 spinner 之前。
